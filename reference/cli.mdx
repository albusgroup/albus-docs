Look up an `albus` command, flag, or environment variable. The CLI is a thin shell
over the [Python SDK](/reference/sdks): each command that calls Albus maps to one
API operation and prints the JSON response on stdout, so output pipes into `jq`.

```bash
albus sessions get my-session | jq '.messages[-1].content'
albus sessions run my-session -p hello --agent-name demo --model gemini-3.6-flash \
  | jq -r '.message.content'
```

## Global options

| Option | Meaning |
|---|---|
| `--base-url` | API base URL. Overrides `ALBUS_BASE_URL`; defaults to `https://albus.sh/api`. |
| `--timeout` | Per-request timeout in seconds (default 30). A waiting `sessions run` long-polls and is exempt. |
| `--version` | Print the CLI version. |
| `--help` | Available on every command and subcommand. |

## Environment

| Variable | Read by | Meaning |
|---|---|---|
| `ALBUS_API_KEY` | CLI | Organization API key. Wins over a stored session. |
| `ALBUS_BASE_URL` | CLI | Default API base URL. |
| `ALBUS_CONFIG_DIR` | CLI | Where the browser session is stored. Falls back to `$XDG_CONFIG_HOME/albus`, then `~/.config/albus`. |
| `ALBUS_API_KEY` | SDKs | Organization API key, when the client is constructed with no credential. |
| `ALBUS_BEARER_AUTH` | SDKs | User bearer token, likewise. |

## Authentication

```bash
albus login                # browser sign-in
albus login --no-browser   # print the URL for you to open, and wait
albus logout
albus whoami               # the caller the credential in effect authenticates
albus status               # what credential is in effect, and whether it works
albus health
albus --version
```

`albus whoami` sends whichever credential precedence resolves — an exported
`ALBUS_API_KEY` first, then the stored session — and names what it
authenticates: `user` for a session, `api_key` for a key.

`albus status` prints JSON and exits 0 whether or not the credential works:
`cli_version`, `base_url`, `credential` (`api_key`, `session`, or `none`),
`authenticated`, plus `caller` (the `/whoami` body) for a credential Albus
accepted and `error` for one it refused.

## Sessions

```bash
albus sessions run SESSION_ID --prompt TEXT --agent-name NAME [options]
albus sessions list
albus sessions get SESSION_ID [--after CURSOR] [--limit N]     # limit defaults to 100
albus sessions audit SESSION_ID [--after CURSOR] [--limit N]   # limit defaults to 100
albus sessions delete SESSION_ID
```

`sessions run` options:

| Option | Meaning |
|---|---|
| `--prompt`, `-p` | The user prompt. Required. |
| `--agent-name` | Name identifying the agent. Required. |
| `--model` | Model identifier. Required unless `--agent-file` is given. |
| `--provider` / `--credential` | Your own provider and its secret reference. Must be given together. |
| `--system-prompt` | System instructions. |
| `--tool` | A built-in tool the model may call — `web_search` or `terminal`. Repeat to allow several. |
| `--max-steps` | Cap on model steps. |
| `--agent-file` | JSON file holding the whole agent configuration. Cannot be combined with the options above. |
| `--invocation-key` | Names the invocation: makes the run retry-safe, and is what reads it back by key. |
| `--wait` / `--no-wait` | Block for the reply (default) or return once accepted. |
| `--wait-timeout` | Seconds to block server-side, up to `1800`. Omit for the server's 30-minute default. |

`--wait` and `--wait-timeout` are the CLI's spelling of the API's
`wait_timeout_seconds` query parameter: `--wait --wait-timeout 120` sends `120`,
`--wait` alone omits the parameter and takes the server's 30-minute default, and
`--no-wait` sends `0`, so the call returns once the invocation is accepted.

`sessions run` prints the API response — the `session` and the one `message`
this invocation produced — plus one key the CLI adds, `invocation_key`: the
effective key of the invocation, which you resend to re-attach to a run, and
which `GET /traces/{invocation_key}` reads it back by. The whole conversation
comes from `albus sessions get`, whose `messages` holds every turn. See [Run a
session](/guides/run-a-session).

<Note>
Over HTTP the key travels as the `Idempotency-Key` header, which is the name it
keeps in the API reference; the CLI and the SDKs call it the invocation key.
</Note>

## Models

```bash
albus models list
```

The models `--model` accepts, and the provider each runs on. See [Model
providers](/guides/model-providers).

## Secrets

```bash
albus secrets list
albus secrets create NAME [--value VALUE]   # omit --value to read stdin
albus secrets get NAME                      # masked
albus secrets update NAME [--value VALUE]
albus secrets delete NAME
```

See [Secrets](/guides/secrets).

## Invites

```bash
albus invites create EMAIL
```

Invites a person by email; they get their own organization when they first sign
in. Needs the browser session, like `tokens`.

## Agents

```bash
albus agents list
albus agents get NAME
albus agents revision NAME REVISION
```

See [Agents and revisions](/guides/agents-and-revisions).

<Note>
Traces and memories have no CLI commands yet — read them over HTTP, from the
[SDKs](/reference/sdks#traces-memories-and-models), or in the console.
</Note>

## API keys

```bash
albus tokens list
albus tokens create NAME    # prints the only copy of the value
albus tokens get ID
albus tokens delete ID
```

`tokens` requires the browser session, since minting a key identifies you. See
[Authenticate](/getting-started/authenticate).

## Exit codes

`0` on success, `1` on any failure. A failure prints two lines on stderr and no
traceback:

```text
albus: <what the server or the client refused>
albus: docs: https://docs.albus.sh/guides/troubleshooting
```

`albus status` is the exception: it exits `0` even when the credential is
rejected, and reports the refusal in its JSON `error` field.
