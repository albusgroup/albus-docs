Albus runs agent sessions over an HTTP API. A **session** is a named
conversation with an agent: you choose the identifier, and running the same
identifier again continues that conversation. One HTTP call runs a turn and
returns the assistant's reply.

You are probably reading this to set Albus up for the user of this machine, or to
write code against it. Both are below, in order. Do not skip verification.

## Private-beta limits

Read these before designing anything.

- **20 session runs per organization**, ever, in the private beta. `429` means the
  cap is spent. Never retry a run in a loop.
- **Access is by invitation.** A `403` naming `not_provisioned` means the account
  is not enabled: stop and tell the user to email carlo@albus.sh with the Google
  address they sign in with.
- **One invocation per session at a time.** A second one gets `423`. Concurrency
  lives across session ids.
- **Bounded retries.** Albus retries a crashed invocation up to three attempts;
  past that it fails with `502` and does not resume.
- **No usage or billing surface.** Consumption is metered but not readable, apart
  from per-invocation token usage on traces.
- **Observability is traces plus the per-session audit log** — no metrics,
  dashboards, or alerting. Trace spans are kept for 90 days.

Full detail: [private-beta limitations](/beta/limitations).

## Setup

### 1. Install the CLI

```bash
curl -fsSL https://albus.sh/install.sh | sh
```

On Windows: `irm https://albus.sh/install.ps1 | iex`.

The installer uses `uv tool install`, then `pip install --user`, then conda. If
`albus` is not on `PATH` afterwards, it is in the scripts directory the installer
printed (usually `~/.local/bin`).

### 2. Check what state you are in

```bash
albus status
```

```json
{
  "cli_version": "0.5.0",
  "base_url": "https://albus.sh/api",
  "credential": "none",
  "authenticated": false
}
```

`credential` is `api_key` when `ALBUS_API_KEY` is set, `session` when the user is
signed in, `none` otherwise. A credential Albus accepted also reports `caller`,
the `/whoami` body naming whoever it authenticates; one that does not work
reports `error`. The command
exits 0 either way — read the JSON, not the exit code. If `authenticated` is
already `true`, skip to step 4.

### 3. Authenticate

You cannot complete a browser sign-in yourself. Print the URL and let the user
open it.

```bash
albus login --no-browser
```

The command prints the authorization URL on its own line, then blocks until the
user finishes, for up to 180 seconds. Show the URL verbatim and ask them to open
it. Do not open a browser on their behalf, and do not paste their credentials
anywhere.

The sign-in redirects to `127.0.0.1:8484-8487` on the machine running the CLI. If
that is not the machine the user's browser is on, tell them to forward those four
ports from their own machine:

```bash
ssh -L 8484:localhost:8484 -L 8485:localhost:8485 \
    -L 8486:localhost:8486 -L 8487:localhost:8487 user@this-host
```

Or have them sign in on their own machine and set `ALBUS_API_KEY` here instead.
An organization API key needs no browser:

```bash
export ALBUS_API_KEY="alb-9pv2rk3n-1f4c8a6b2d9e7c50a3b81df6"
```

### 4. Verify

```bash
albus whoami
```

JSON naming the caller means setup is complete: `whoami` accepts either
credential and reports which one signed the request. An error naming the Albus
beta means the account is not provisioned — stop, and tell the user to email
carlo@albus.sh.

### 5. Run one session

Do this once, to prove the setup end to end. It spends one of the organization's
20 private-beta runs, so run it once and do not loop.

```bash
albus sessions run setup-check \
  --prompt "Reply with exactly: albus is working" \
  --agent-name setup-check \
  --model gemini-3.6-flash
```

The assistant's reply is `message.content`. The printed `invocation_key` names
that run — it is what reads its trace back later.

### 6. Install an SDK, if the user is writing code

```bash
pip install albus-sdk          # Python
npm install @albus-ts/sdk      # TypeScript
```

Both authenticate with an organization API key, which is a different credential
from the browser session. Minting one requires the browser session from step 3:

```bash
albus tokens create local-dev
```

The `token` field is shown once. Have the user store it, then:

```bash
# One variable for every client: the CLI and both SDKs read ALBUS_API_KEY.
export ALBUS_API_KEY="alb-9pv2rk3n-1f4c8a6b2d9e7c50a3b81df6"
```

Never write the key into a source file, a committed config, or a shell profile
you did not create for this purpose.

## The whole API surface

Base URL `https://albus.sh/api`. Authenticate with `Authorization: Bearer <key>`.

| Operation | HTTP | CLI |
|---|---|---|
| Run or resume a session | `POST /sessions/{id}` | `albus sessions run ID -p TEXT --agent-name NAME --model NAME` |
| List sessions | `GET /sessions` | `albus sessions list` |
| Get a session and its messages | `GET /sessions/{id}` | `albus sessions get ID` |
| Audit what happened in it | `GET /sessions/{id}/audit` | `albus sessions audit ID` |
| Delete a session | `DELETE /sessions/{id}` | `albus sessions delete ID` |
| Store a credential | `POST /secrets` | `albus secrets create NAME --value V` |
| List, read, update, delete secrets | `/secrets`, `/secrets/{name}` | `albus secrets list\|get\|update\|delete` |
| List agents, get one | `GET /agents`, `GET /agents/{name}` | `albus agents list\|get` |
| Get the exact configuration a run used | `GET /agents/{name}/revisions/{revision}` | `albus agents revision NAME REVISION` |
| List invocations across sessions | `GET /traces` | — |
| Read one invocation and its spans | `GET /traces/{invocation_key}` | — |
| List a memory group | `GET /memories?group=NAME` | — |
| Delete a memory, or a whole group | `DELETE /memories/{id}?group=NAME`, `DELETE /memories?group=NAME` | — |
| List the models Albus serves | `GET /models` | `albus models list` |
| Mint or manage API keys | `/tokens` | `albus tokens create\|list\|get\|delete` |
| Invite someone | `POST /invites` | `albus invites create EMAIL` |
| Who am I | `GET /whoami` | `albus whoami` |
| Service health | `GET /health` | `albus health` |

Everything above accepts an organization API key or a user bearer token, except
`/tokens` and `/invites`, which identify *you* and take the browser session only.
Traces and memories have no CLI commands yet.

### Running a session

```http
POST /sessions/support-1234?wait_timeout_seconds=120
Authorization: Bearer <key>
Content-Type: application/json
Idempotency-Key: support-1234-summary-v1

{
  "user_prompt": "Summarize this ticket for the on-call engineer.",
  "agent_name": "support-triage",
  "agent": {
    "model": { "name": "gemini-3.6-flash" },
    "system_prompt": "You triage support tickets. Be terse.",
    "tools": { "web_search": {}, "terminal": {} },
    "memory": { "group": "support", "generation": ["end_of_invocation"] },
    "max_steps": 12,
    "mcp_servers": [
      {
        "name": "github",
        "url": "https://api.githubcopilot.com/mcp/",
        "headers": { "Authorization": "albus.sh/secrets/integrations/github/token" },
        "allowed_tools": ["search_issues", "get_issue"]
      }
    ]
  }
}
```

- `wait_timeout_seconds=<n>` blocks up to `n` seconds until the assistant replies
  and returns the session with the one `message` this invocation produced — the
  whole conversation is `GET /sessions/{id}`, whose `messages` holds every turn.
  `1800` is the maximum, and what an
  omitted parameter means. `wait_timeout_seconds=0` does not wait: it returns as
  soon as the run is accepted, and you poll `GET /sessions/{id}` until
  `session.state` leaves `RUNNING`.
- Exceeding the wait is `504`, and the run is still going.
- The CLI spells the same thing as `--wait`/`--no-wait` and `--wait-timeout`:
  `--wait` (the default) with no `--wait-timeout` omits the parameter, and
  `--no-wait` sends `0`. Both SDKs default the wait to `1800` and give the run a
  31-minute transport timeout, so a waiting run needs no client configuration.
- Omitting `agent.model.provider` uses the model credential Albus supplies, which
  is what a first run should do. To bring your own, store it as a secret and
  reference it — see [model providers](/guides/model-providers).
- `mcp_servers` requires a Streamable HTTP MCP endpoint. `allowed_tools` names
  tools as the server names them; the agent sees them prefixed, as
  `github__search_issues`. Omit it to allow every tool the server exposes. See
  [MCP servers](/guides/mcp-servers).
- `tools` is an object, not a list: include a tool's block to offer it, omit it
  to withhold it. `web_search` searches the web, `terminal` gives the model a
  persistent Linux sandbox to run commands in.
- `memory` gives the agent durable memory shared by every invocation configured
  with the same `group`, whichever session it runs in. `generation` lists when it
  may write: `end_of_invocation`, `agent`, or both.
- `output_format` takes a JSON Schema the answer must conform to, and the reply
  comes back as a JSON document. Every object in the schema must set
  `"additionalProperties": false` and list every property in `"required"`, and
  the model has to be one that supports structured output.
- The model must be one `GET /models` lists, unless `agent.model.provider` names
  your own account; an unserved model is `400`.

### Reading an invocation back

```http
GET /traces?agent_name=support-triage&status=FAILED&limit=20
GET /traces/support-1234-summary-v1?attempts=all
```

The detail response is the invocation — status, timings, failure — plus its
**spans**: every step, model call, and tool call, with the payloads they carried.
Defaults and knobs: only the latest attempt's spans unless `attempts=all`,
`payloads=false` to drop payloads and page more spans at once, `after` to page.
`attempts` lists every attempt with its own outcome and usage. Spans live 90
days; past that `spans_expired` is true and the invocation itself still reads.

List filters: `agent_name`, `agent_revision`, `status`, `session_id`, `since`,
`until`, `after`, `limit`. A `503` may carry `Retry-After`.

### Failures and what to do about them

| Status | Meaning | Do |
|---|---|---|
| `400` | The agent configuration or prompt is invalid | Fix the request; do not retry as-is |
| `401` | Credential rejected | `albus status`, then re-authenticate |
| `403` | Not provisioned for the private beta | Stop; the user emails carlo@albus.sh |
| `404` | No such session, secret, agent, revision, or token | Check the identifier |
| `409` | The invocation key was reused with a different body | Use a new key, or resend the original body |
| `423` | Another invocation is running in that session | Wait, re-send the running key to attach, or use a different session id |
| `429` | The organization's 20 runs are spent | Stop; the user emails carlo@albus.sh |
| `502` | Every attempt of the invocation failed | Read `GET /traces/{invocation_key}` or `albus sessions audit ID`; a new invocation key reruns it |
| `504` | The wait elapsed, the run continues | Re-send with the **same** invocation key, or poll |

## Rules that matter when you write Albus code

- **The session id is the caller's.** The same id resumes the conversation; a new
  id starts one. Do not generate a fresh id per turn.
- **Pass an invocation key** on anything unattended, derived from the work item
  rather than the clock. The same key re-attaches to that invocation instead of
  running again — which makes it right for a lost response or a `504`, and wrong
  for rerunning a failed invocation. That needs a new key.
- **One invocation per session at a time.** Concurrency lives across session ids,
  not inside one.
- **Credentials are never inlined.** Store them with `albus secrets create` and
  reference them as `albus.sh/secrets/<name>`. Required for
  `model.provider.credential`, correct for MCP headers. Values are resolved
  server-side and never appear in responses or the audit log.
- **`--agent-file` replaces the other agent flags** and cannot be combined with
  them.
- **The invocation key has two names.** It is `invocation_key=` in Python,
  `invocationKey:` in TypeScript, `--invocation-key` in the CLI, and the
  `Idempotency-Key` header over HTTP — one value, and what `GET /traces/{...}`
  looks an invocation up by.

## Examples

### Run and resume a session

<CodeGroup>

```python Python
import os

from albus_sdk import Albus

SESSION = "example-resume"
AGENT = {"model": {"name": "gemini-3.6-flash"}}

with Albus(
    api_key=os.environ["ALBUS_API_KEY"],
) as albus:
    for prompt in ["Name three primary colors.", "Now sort them alphabetically."]:
        response = albus.sessions.run_session(
            id=SESSION,
            user_prompt=prompt,
            agent_name="example",
            agent=AGENT,
            wait_timeout_seconds=300,
        )
        print(response.result.message.content)
```

```typescript TypeScript
import { Albus } from "@albus-ts/sdk";

const albus = new Albus({
  security: { apiKey: process.env.ALBUS_API_KEY ?? "" },
});

const session = "example-resume";
const agent = { model: { name: "gemini-3.6-flash" } };

for (const userPrompt of [
  "Name three primary colors.",
  "Now sort them alphabetically.",
]) {
  const response = await albus.sessions.runSession({
    id: session,
    waitTimeoutSeconds: 300,
    body: { userPrompt, agentName: "example", agent },
  });

  console.log(response.result.message?.content);
}
```

```bash CLI
albus sessions run example-resume -p "Name three primary colors." \
  --agent-name example --model gemini-3.6-flash
albus sessions run example-resume -p "Now sort them alphabetically." \
  --agent-name example --model gemini-3.6-flash
```

</CodeGroup>

### Run unattended, retry safely

The key is derived from the work item, not the clock, so a retry re-attaches
instead of running twice. The wait is bounded, and a timeout means "still
running".

```python Python
import os

from albus_sdk import Albus, errors

TICKET = "support-1234"

with Albus(
    api_key=os.environ["ALBUS_API_KEY"],
) as albus:
    for attempt in range(3):
        try:
            response = albus.sessions.run_session(
                id=TICKET,
                user_prompt="Summarize this ticket for the on-call engineer.",
                agent_name="support-triage",
                agent={"model": {"name": "gemini-3.6-flash"}},
                invocation_key=f"{TICKET}-summary-v1",
                wait_timeout_seconds=120,
            )
            print(response.result.message.content)
            break
        except errors.AlbusError as error:
            # 504: the run is still going — the same key re-attaches to it.
            # 429: the private-beta quota is spent; retrying will not help.
            if error.status_code != 504:
                raise
    else:
        print("still running after three waits")
```

### Give the agent GitHub tools

```python Python
import os

from albus_sdk import Albus

with Albus(
    api_key=os.environ["ALBUS_API_KEY"],
) as albus:
    albus.secrets.create_secret(
        name="integrations/github/token",
        value=f"Bearer {os.environ['GITHUB_TOKEN']}",
    )

    response = albus.sessions.run_session(
        id="repo-triage",
        user_prompt="Find open issues mentioning login failures and summarize them.",
        agent_name="repo-triage",
        agent={
            "model": {"name": "gemini-3.6-flash"},
            "system_prompt": "You investigate GitHub issues. Cite issue numbers.",
            "mcp_servers": [
                {
                    "name": "github",
                    "url": "https://api.githubcopilot.com/mcp/",
                    "headers": {
                        "Authorization": "albus.sh/secrets/integrations/github/token"
                    },
                    "allowed_tools": ["search_issues", "get_issue"],
                }
            ],
        },
        wait_timeout_seconds=300,
    )
    print(response.result.message.content)
```

### Debug a run

```bash
albus sessions get support-1234
albus sessions audit support-1234 --limit 50 | jq '.events[] | {type, agent_revision, event_time}'
albus agents revision support-triage "$(albus sessions get support-1234 | jq -r '.session.agent_revision')"
```

```python Python
import os

from albus_sdk import Albus

with Albus(api_key=os.environ["ALBUS_API_KEY"]) as albus:
    for summary in albus.traces.list_traces(
        agent_name="support-triage", status="FAILED", limit=10
    ).traces:
        print(summary.invocation_key, summary.session_id, summary.started_at)

    trace = albus.traces.get_trace(
        invocation_key="support-1234-summary-v1", attempts="all"
    ).result
    for span in trace.spans:
        print(span.id, span.type, span.name, span.status)
```

The [audit log](/guides/audit-log) is what happened inside one session's runs,
and traces are the same events across sessions with each attempt's token usage;
`agents revision` is the exact configuration that ran it.

### Fan out across sessions

```python Python
import asyncio
import os

from albus_sdk import AsyncAlbus

TICKETS = ["support-1", "support-2", "support-3"]


async def summarize(albus: AsyncAlbus, ticket: str) -> str:
    response = await albus.sessions.run_session(
        id=ticket,
        user_prompt="Summarize this ticket.",
        agent_name="support-triage",
        agent={"model": {"name": "gemini-3.6-flash"}},
        invocation_key=f"{ticket}-summary-v1",
        wait_timeout_seconds=300,
    )
    return response.result.message.content


async def main() -> None:
    async with AsyncAlbus(
        api_key=os.environ["ALBUS_API_KEY"],
    ) as albus:
        for summary in await asyncio.gather(
            *(summarize(albus, ticket) for ticket in TICKETS)
        ):
            print(summary)


asyncio.run(main())
```

<Warning>
Each run spends one of the organization's 20 private-beta runs. Fan out
deliberately.
</Warning>
